# Consent Dialog

Fork CMS ships with a built-in privacy consent dialog that is fully aligned with **Google Consent Mode v2**. This guide covers how the system works, how to configure Google Tag Manager to use the consent signals, and how to read consent status in your own module code.

For the admin-facing configuration (enabling the dialog, choosing levels) see the [Settings user guide](../03.%20user%20guide/09.%20settings.md#privacy). For theming the dialog template see the [Consent Dialog theming guide](../04.%20theming%20guide/10.%20privacy_consent_dialog.md).

---

## How it works

When the consent dialog is enabled, Fork injects a consent initialisation block into the `<head>` **before** Google Tag Manager loads:

```html
<script>
  window.dataLayer = window.dataLayer || [];
  function gtag(){dataLayer.push(arguments);}
  gtag('consent', 'default', {
    "ad_storage": "denied",
    "ad_user_data": "denied",
    "ad_personalization": "denied",
    "analytics_storage": "denied",
    "functionality_storage": "granted",
    "personalization_storage": "denied",
    "security_storage": "denied"
  });
</script>
```

If the visitor has already stored their preferences (returning visit), their choices are applied in the same server-rendered block before GTM fires:

```html
  gtag('consent', 'update', {"analytics_storage":"granted","ad_storage":"denied",...});
```

This means GTM never fires optional tags before the visitor has consented, and returning visitors never lose their approved tags on page load.

When a visitor makes or changes a choice in the dialog, the JavaScript layer calls:

```js
gtag('consent', 'update', { analytics_storage: 'granted', ad_storage: 'denied', ... })
```

Consent choices are stored in cookies named `privacy_consent_level_[level]_granted` (value `1` or `0`, expires after six months).

## Setting up Google Tag Manager

### 1. Enable Consent Overview in GTM

In your GTM container go to **Admin → Container Settings** and enable **Enable consent overview**. This adds a shield icon next to each tag so you can see and configure its consent requirements.

### 2. Enable built-in consent for Google tags

If you are using the **Google Analytics 4 Configuration** tag or any Google Ads tag, consent is handled automatically once Consent Mode is initialised. Open each tag and confirm the **Consent Settings** section shows the correct consent type (e.g. `analytics_storage` for GA4). Google's own tags will respect the signal without further configuration.

### 3. Add consent requirements to custom tags

For any custom or third-party tag that should only fire when the visitor has given a specific consent:

1. Open the tag in GTM.
2. Click **Consent Settings** (the shield icon).
3. Set **Require additional consent for tag to fire** and choose the appropriate consent type.

The consent types available match the levels configured in Fork's Settings page:

| GTM consent type | Fork level |
|---|---|
| `ad_storage` | Advertising cookies |
| `ad_user_data` | Ad user data |
| `ad_personalization` | Ad personalization |
| `analytics_storage` | Analytics cookies |
| `functionality_storage` | Functional cookies (always granted) |
| `personalization_storage` | Personalization cookies |
| `security_storage` | Security cookies |

### 4. Verify in GTM Preview

Use GTM's **Preview** mode and open the **Consent** tab. You will see the consent state for each signal at each point during page load:

- On a first visit all optional signals show **Denied** at page load, then update to **Granted** after the visitor accepts in the dialog.
- On a returning visit where consent was previously given, signals show **Granted** from the very first event because Fork applies the stored choices server-side before GTM loads.

## Reading consent in PHP

Use `ConsentDialog::hasAgreedTo()` to check whether the current visitor has consented to a specific level. The service is available from the DI container.

```php
use ForkCMS\Privacy\ConsentDialog;

if ($consentDialog->hasAgreedTo(ConsentDialog::LEVEL_ANALYTICS_STORAGE)) {
    // only run analytics-dependent code when the visitor has agreed
}
```

The full list of constants:

```php
ConsentDialog::LEVEL_AD_STORAGE
ConsentDialog::LEVEL_AD_USER_DATA
ConsentDialog::LEVEL_AD_PERSONALIZATION
ConsentDialog::LEVEL_ANALYTICS_STORAGE
ConsentDialog::LEVEL_FUNCTIONALITY_STORAGE  // always true
ConsentDialog::LEVEL_PERSONALIZATION_STORAGE
ConsentDialog::LEVEL_SECURITY_STORAGE
```

You can also fetch the complete set of visitor choices as an associative array:

```php
$choices = $consentDialog->getVisitorChoices();
// ['functionality_storage' => true, 'analytics_storage' => false, ...]
```

## Listening for consent changes in JavaScript

When a visitor saves their preferences, `jsFrontend.consentDialog` dispatches a jQuery event on the document:

```js
$(document).on('privacyConsentChanged', function () {
    // re-evaluate anything that depends on consent
})
```

The current choices are always available via:

```js
jsData.privacyConsent.visitorChoices
// { functionality_storage: true, analytics_storage: true, ad_storage: false, ... }
```

## Deploying a consent configuration change

If you change which levels are enabled in Settings, the consent hash changes. Every visitor will see the consent dialog again on their next visit and must re-confirm, because their previous consent no longer covers the updated set of levels.

After deploying changes to locale XML files, re-import translations via **Settings → Translations → Import** to ensure the dialog labels appear correctly.
